# PingUp 2.1.0 — обновление

Этот документ состоит из двух частей: обновление работающей установки **2.0.0-beta.1 → 2.1.0** (ниже) и, для старых установок, переход **1.1 → 2.0** на PostgreSQL (приложение в конце). Если вы ещё на 1.1, сначала выполните приложение (импорт создаст сразу схему 5), затем пункты 3–7 этой части.

## 0. Автоматическое обновление одной командой

Загрузите архив на сервер (например, в `/root`) и выполните:

```bash
cd /root
unzip -o -j pingup-php-2.1.0-postgresql.zip PingUp/update.sh
sudo bash update.sh --check                                   # только проверка, ничего не меняет
sudo bash update.sh pingup-php-2.1.0-postgresql.zip           # обновление
```

`update.sh` сам находит установку (служба `pingup-push`, корень сайта в Nginx или `/var/www/pingup`; иначе `--app-dir`), читает настройки БД из `config.local.php` или из окружения PHP-FPM/systemd и выполняет:

1. Проверки: архив по SHA256SUMS, PHP 8.2+ и расширения (недостающие ставит через apt), подключение к PostgreSQL, схема 4, `pg_dump` нужной версии, место на диске, список локально изменённых файлов 2.0.
2. Резервную копию в `/var/backups/pingup/2.1-update-<дата>/` (0700): дамп БД, код с `config.local.php`, журнал.
3. Лимиты для загрузки частями: `post_max_size 20M` / `upload_max_filesize 16M` для PHP-FPM и `client_max_body_size 20m` в Nginx, только если текущие меньше (с `nginx -t` и возвратом при ошибке).
4. Миграцию 4 → 5, пока работает 2.0 (схема только расширяется). При ошибке PostgreSQL откатывает транзакцию, 2.0 продолжает работать.
5. Замену кода на месте: `config.local.php` и `storage/` не трогаются, права и владельцы сохраняются, файлы 2.0, которых нет в 2.1, удаляются, результат сверяется с SHA256SUMS. При сбое код 2.0 возвращается автоматически.
6. Перезагрузку PHP-FPM (сброс OPcache), службу `pingup-mail` (включается, если настроен SMTP) и таймер `pingup-cleanup` раз в 5 минут (без systemd — `/etc/cron.d/pingup`). Переменные окружения из `pingup-push` переносятся в новые службы.
7. Проверку: `bin/doctor.php`, ответ API версии 2.1.0 и `sw.js` 2.1.0 по `app_origin`.

Простой — несколько секунд. Откат к 2.0 (код и БД из резервной копии; данные, созданные после обновления, теряются, но перед откатом сохраняется дамп 2.1):

```bash
sudo bash /var/backups/pingup/2.1-update-<дата>/update.sh --rollback /var/backups/pingup/2.1-update-<дата>
```

Повторный запуск после успешного обновления ничего не меняет (`--force` — заново разложить код). Ключи: `--yes` без подтверждения, `--skip-web` не трогать Nginx/PHP, `--backup-root DIR`.

Скрипт не настраивает SMTP и не создаёт администратора — подскажет команды в конце. Разделы ниже описывают те же шаги вручную.

## 1. Что меняется

- Схема БД **4 → 5** (`database/migrations/005_messenger_2_1.sql`): только добавления — новые таблицы (контакты, блокировки, приватность, подписки Premium, аудит, обратная связь, e-mail, приглашения, баны, статистика, опросы, стикеры, папки, отложенные сообщения, загрузка частями) и столбцы. Пользовательские данные не удаляются. Для существующих данных вычисляются: роль `owner` у владельцев групп и каналов, курсор доставки = курсор прочтения, время закрепления = время изменения.
- Фронтенд заменён: `styles.css`, `experience.css`, `motion.css` удалены; добавлены `app.css`, `ui.js`, `chat.js`, `pages.js`, `settings.js`, `assets/stickers/*`. Service Worker 2.1.0 сам удалит кэш 2.0 после активации.
- Новые фоновые задачи: отправка писем (`bin/mail-worker.php`) и cron `bin/cleanup.php` (публикует отложенные сообщения, удаляет брошенные загрузки и устаревшие строки). Отложенные публикации дополнительно выпускаются при синхронизации клиентов, но cron обязателен для надёжности.
- Лимит файла по умолчанию: 50 МБ, с Premium 200 МБ (`max_upload_bytes`, `premium_upload_bytes`). Файлы идут частями по 8 МБ, поэтому лимиты Nginx/PHP остаются небольшими: `client_max_body_size 20m`, `upload_max_filesize=16M`, `post_max_size=20M`.

## 2. Резервная копия

Включите maintenance, остановите `pingup-push`, дождитесь окончания звонков. Сделайте дамп и копию приватного хранилища:

```bash
pg_dump --format=custom --host=127.0.0.1 --username=pingup --file=/PRIVATE_BACKUP_PATH/pingup-before-2.1.dump pingup
sudo tar -C /var/www/pingup -czf /PRIVATE_BACKUP_PATH/pingup-storage-before-2.1.tgz storage config.local.php
```

## 3. Код и конфигурация

Распакуйте архив в новый каталог, перенесите `config.local.php` и приватное `storage/` (uploads, sessions, `vapid.json`). Новый параметр `app_secret` не обязателен: при первом обращении к e-mail функциям создаётся `storage/app-secret.key` (0600) — сохраняйте его в резервных копиях, иначе выданные коды станут недействительными (сами аккаунты не пострадают).

Добавьте в `config.local.php` (пример — в `config.local.example.php`):

```php
'max_upload_bytes' => 50 * 1024 * 1024,
'premium_upload_bytes' => 200 * 1024 * 1024,
'smtp_host' => 'smtp.example.com',
'smtp_port' => 587,
'smtp_secure' => 'tls',          // tls = STARTTLS, ssl = 465, none — только локальный relay
'smtp_user' => 'pingup@example.com',
'smtp_password' => 'SMTP_PASSWORD',
'mail_from' => 'no-reply@example.com',
'mail_from_name' => 'PingUp',
```

Пароль SMTP храните только в `config.local.php` (0640 root:www-data) или в окружении сервиса (`PINGUP_SMTP_*`), никогда в public/. Без SMTP приложение работает, а письма копятся в очереди (`bin/doctor.php` показывает её размер).

## 4. Миграция

```bash
sudo -u www-data php bin/migrate.php     # Applied migration 005_messenger_2_1.sql / PostgreSQL schema 5 ready.
sudo -u www-data php bin/doctor.php
```

Миграция выполняется в одной транзакции под advisory lock; при ошибке база остаётся в схеме 4. Повторный запуск ничего не меняет. Роль, выполняющая миграцию, должна владеть таблицами (как и для 2.0).

## 5. Службы, cron, веб-сервер

```bash
sudo cp deploy/pingup-mail.service /etc/systemd/system/ && sudo systemctl enable --now pingup-mail
sudo cp deploy/pingup.cron /etc/cron.d/pingup
sudo cp deploy/php-fpm-pingup.ini /etc/php/8.3/fpm/conf.d/90-pingup.ini && sudo systemctl reload php8.3-fpm
sudo nginx -t && sudo systemctl reload nginx     # client_max_body_size 20m из deploy/nginx.conf
sudo systemctl start pingup-push
```

Пути в unit-файлах и cron адаптируйте к вашему каталогу. Если администратора ещё нет — `php bin/create-admin.php` (обратная связь и выдача Premium доступны только роли admin).

## 6. Проверка перед открытием трафика

Вход двух пользователей; отправка с галочками (одна → две серые после открытия приложения получателем → цветные после просмотра); контакты и приватность; поиск; создание канала с оформлением; файл больше 8 МБ (загрузка частями) и проверка 50 МБ; обращение со скриншотом и ответ администратора; e-mail-код (реальный SMTP); обновление PWA (кнопка «Обновить»). На Android проверьте кнопку «Назад», клавиатуру и жесты на реальном устройстве.

## 7. Откат

До новых записей: остановите трафик, восстановите дамп `pingup-before-2.1.dump` (`pg_restore --clean`) и код 2.0. После начала работы 2.1 откат к 2.0 возможен восстановлением того же дампа с потерей данных, созданных в 2.1; схема 5 обратно в 4 автоматически не преобразуется. Код 2.0 со схемой 5 не запускайте: `bin/migrate.php` 2.0 откажется работать с неизвестной схемой.

# Приложение: переход 1.1 (SQLite) → 2.0 (PostgreSQL)

Предыдущая сборка 1.1 сохранена отдельно. Новая версия требует PostgreSQL 15+ (проверена 17.11), расширение pg_trgm и PHP pdo_pgsql. При запуске HTTP схема автоматически не создаётся: миграция выполняется CLI перед запуском трафика. Продакшен app.pingup.cc здесь не менялся.

## 1. Резервная копия и остановка записи

Включите maintenance в Nginx, остановите старый Push worker и завершите звонки. Сохраните старую версию кода, config.local.php, VAPID-ключи, uploads и при необходимости sessions. SQLite-базу копируйте через backup API, чтобы не потерять данные WAL:

```bash
sudo -u www-data sqlite3 /var/www/pingup/storage/pingup.sqlite '.backup /PRIVATE_BACKUP_PATH/pingup-schema3.sqlite'
```

PRIVATE_BACKUP_PATH замените приватным каталогом, доступным www-data. Проверьте `PRAGMA user_version;`: импорт ожидает **3**. Для схемы 1/2 сначала обновите отдельную копию старым PingUp 1.1 (`bin/migrate.php` из версии 1.1), не командой нового PostgreSQL-релиза. Исходную базу не удаляйте. Не открывайте запись одновременно в старом и новом приложении.

## 2. PostgreSQL и PHP

Пример для Ubuntu с доступным PHP 8.3; имена пакетов адаптируйте к вашей ОС:

```bash
sudo apt install postgresql postgresql-contrib php8.3-pgsql php8.3-sqlite3 php8.3-mbstring php8.3-curl php8.3-gmp
sudo -u postgres createuser --pwprompt pingup
sudo -u postgres createdb --owner=pingup pingup
```

Пароль вводится интерактивно, не аргументом команды. Роль не должна быть superuser. Для первоначальной миграции роль — владелец БД и схемы public: миграция создаёт таблицы/триггеры и trusted extension pg_trgm. После развёртывания можно отделить роль миграций от runtime-роли, выдав последней права на таблицы и последовательности. SQL SECURITY DEFINER не используется.

Для удалённого PostgreSQL используйте приватную сеть, ограниченный firewall и TLS с проверкой сертификата (`sslmode=verify-full;sslrootcert=/private/root.crt`). Не открывайте порт 5432 всему Интернету. Локальный PostgreSQL может использовать loopback, SCRAM и `sslmode=prefer`.

## 3. Новый код и конфигурация

Распакуйте архив в **новый каталог**. DocumentRoot — только public/. Перенесите приватные uploads/sessions/VAPID из предыдущей установки, задайте соответствующие storage_path/upload_dir/session_dir/vapid_file. Не копируйте пустую storage поверх пользовательских данных.

Сохраните старые app_origin, secure_cookies, invite_code, max_users и TURN. Удалите старый параметр db_path; добавьте в config.local.php:

```php
'database_dsn' => 'pgsql:host=127.0.0.1;port=5432;dbname=pingup;sslmode=prefer',
'database_user' => 'pingup',
'database_password' => 'YOUR_DATABASE_PASSWORD',
```

Альтернатива — PINGUP_DATABASE_DSN, PINGUP_DATABASE_USER, PINGUP_DATABASE_PASSWORD в приватной конфигурации PHP-FPM и systemd. config.local.php имеет приоритет над переменными окружения. FPM по умолчанию может очищать env: настройте pool env[...] либо используйте приватный config.local.php. Не храните секреты в public/, shell history, тестах и ZIP. Права config.local.php — например 0640 root:www-data. Код должен читаться www-data, но не требовать записи от веб-процесса: каталоги 0750 root:www-data, обычные файлы 0640 root:www-data (либо стандартные 0755/0644 для публичной статики). storage принадлежит www-data, каталоги 0700; приватные ключи 0600. После распаковки настройте владельцев перед doctor.php.

vendor включён в архив. При установке самостоятельно:

```bash
composer install --no-dev --prefer-dist --no-interaction --optimize-autoloader
sudo -u www-data php bin/migrate.php
```

Миграция под блокировкой PostgreSQL создаёт схему 4 одной транзакцией; повторный запуск схемы 4 безопасен. Существующая неизвестная схема не заменяется. Ни одна команда не удаляет старую SQLite.

## 4. Импорт из SQLite

Только для существующего проекта, только в **пустую** PostgreSQL-базу:

```bash
sudo -u www-data php bin/import-sqlite.php --source=/PRIVATE_BACKUP_PATH/pingup-schema3.sqlite
sudo -u www-data php bin/doctor.php
```

Импорт читает SQLite с query_only и сохраняет числовые ID, password_hash, session_version, роли, профиль, участников, прочтение/закрепы/настройки уведомлений, сообщения/ответы/пересылки/реакции, вложения, звонки/сигналы и Push-подписки/очередь. Вложения — ссылки на файлы: сами uploads копируются отдельно. Сессии остаются файловыми; для сохранения действующих входов на том же домене перенесите session_dir и session_name. При подозрении на компрометацию сессии отзываются отдельной операцией.

Таблицы назначения блокируются на время импорта. Весь импорт — одна транзакция с отложенными внешними ключами и проверкой количества строк; заполненная цель блокирует команду до изменений. После импорта identity-последовательности выставляются выше существующих ID. При неудаче строк не будет, но PostgreSQL sequence может иметь пропуски: sequence не транзакционна. Это не потеря пользовательских данных.

У старых каналов остаётся приватный доступ, создаются новые случайные приглашения; публичное имя владелец назначает в интерфейсе. Исторические звонки добавляются в соответствующие лички по одной записи. Сигнализация устаревших звонков не нужна для нового WebRTC-сеанса; обновляйте после завершения активных звонков.

## 5. Проверка перед открытием трафика

На копии проверьте вход двух старых пользователей, сообщения/файлы/ответы/реакции, verified администратора, импортированную историю звонков, личное удаление в другой вкладке и глобальное удаление, каналы/приглашения/права читателя, RU/UK/EN и светлую тему. Перед работой с настоящими пользователями сохраните дамп:

```bash
pg_dump --format=custom --host=127.0.0.1 --username=pingup --file=/PRIVATE_BACKUP_PATH/pingup-post-import.dump pingup
```

Пароль вводится штатно или берётся из приватного .pgpass (0600). Не передавайте пароль в URL/аргументе процесса.

Проверьте домен/сертификаты/FPM socket в deploy/nginx.conf, `nginx -t`, затем переключите DocumentRoot на новый public/. Для PHP-FPM включите opcache, display_errors=Off и log_errors=On; перезапустите FPM после смены кода. PostgreSQL autovacuum должен оставаться включённым. Миграции/импорт выполняются ролью с нужными правами; runtime не должен иметь DDL-права без необходимости.

Обновите WorkingDirectory/ExecStart/ReadWritePaths в deploy/pingup-push.service, установите unit и запустите worker по NOTIFICATIONS-CALLS.md. Используйте прежние VAPID-ключи: не создавайте новые при каждом апдейте. Один процесс worker на хост защищён flock; между разными хостами claim защищён FOR UPDATE SKIP LOCKED.

## 6. Новая схема и поведение

- PostgreSQL identity + RETURNING вместо SQLite lastInsertId; время хранится как UNIX bigint.
- schema_migrations.version=4; conversations.description/slug/visibility/avatar_file_id/invite_token.
- message_hidden(user_id,message_id,created_at) для удаления только у себя.
- messages.kind='call' и уникальный call_id. Удаление скрывает карточку, исходная серверная история звонков сохраняется.
- messages.change_seq и sequence message_changes_seq; BEFORE INSERT/UPDATE trigger выдаёт новый курсор под транзакционной блокировкой соответствующего чата. Это предотвращает пропуск позднего commit. Блокировки действуют внутри чата, не сериализуют всё приложение.
- Индексы на дельты/видимую историю/доступ к вложениям, сроки очистки, GIN pg_trgm для поиска людей, текстов и публичных каналов.
- Активный аккаунт видит личное удаление на других устройствах, а удалённый текст не возвращается в поиске, уведомлении, закрепе или ответе. Дельты не изменившегося чата пусты. Нет end-to-end encryption переписки: сервер хранит содержание; WebRTC медиа шифруется транспортом.

## 7. PWA и резервное копирование

SW версии 2.0.0-beta.1 кэширует только перечисленную статику, включая motion.css. Установка загружает свежую статику с cache:reload, чтобы браузерный HTTP-кэш прошлой версии не попал в новый SW-кэш. API, index.php, media.php и приватные ответы не кэшируются. Клиент получает кнопку ручного обновления; обновление во время звонка откладывается. Старые клиенты 1.1 получат предложение обновления, но полноценно поддерживают не все новые функции: попросите тестеров обновить PWA перед приёмкой.

Приватная IndexedDB содержит только собственные ещё не отправленные сообщения и ссылки на вложения; она очищается при явном logout. Локальное устройство с доступом к профилю браузера может читать эти черновики. При переходе домена они не переносятся автоматически.

Резервируйте PostgreSQL через pg_dump/pg_basebackup, а uploads и VAPID отдельно. Не копируйте работающий каталог PostgreSQL простым cp. Не оставляйте дампы в public/.

## 8. Откат и дальнейшее масштабирование

До открытия трафика можно вернуть старую версию и сохранённую SQLite-копию. После новых записей в PostgreSQL возврат старой SQLite потеряет новые сообщения: обратный импорт не реализован. Для отката после открытия трафика сначала включите maintenance, сделайте PostgreSQL-дамп и восстановите совместимую версию/данные. Не обещайте бесшовный downgrade 2.0 → 1.1.

Сейчас веб-приложение использует короткий polling 2 секунды (в фоне 15), WebRTC signaling отдельно, SQLite не используется в runtime. Redis/WebSocket, объектное медиахранилище, распределённые сессии, очереди с отдельным брокером, пагинация каталога больших сообществ, роли редакторов каналов и нагрузочное испытание большого кластера остаются отдельной работой. PostgreSQL улучшает основу, но сама смена БД не делает сервис равным Telegram по масштабу.

Реальная доставка Push, Android PWA, стабильность WebRTC в двух сетях и Coturn на Google Cloud требуют физической приёмки. Инструкции: NOTIFICATIONS-CALLS.md. Проверенное: TEST-RESULTS.md.
